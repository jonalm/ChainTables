ChainTables Concept Map

Several clients agree on a set of tables without a server. The agreement is an append-only, hash-chained sequence of immutable transaction records in an S3 bucket. Each client replays that sequence into its own local copy and reads it through table views. A commit is one put-if-absent to the next slot: the first writer wins, and the loser raises. Anatomy of a transaction record

One deterministic-CBOR map at key <prefix>/000000000042. Every stored byte is hashed. Nothing inside the record names its own hash; the next record does.

; ADR-0006. The encoder sorts keys; this order is expository. ? = optional
{
  "format_version":    1,
  "chain_id":          h'<16>',  ; minted at slot 0
  "slot":              42,
  "prev_hash":         h'<32>',  ; absent at slot 0
  "state_fingerprint": h'<32>',  ; content after apply
  "client":  { "user"?: author, "host"?, "lib", "julia", "time_ms" },
  "comment"?: "…",                ; never read by software
  "ops":     [ … ]                 ; 0 at genesis, ≥1 after
}

transaction_hash  = SHA-256("chaintables/v1/txn" ‖ stored bytes)
table_hash        = SHA-256("chaintables/v1/fp-table" ‖ cbor([shape, rows]))
state_fingerprint = SHA-256("chaintables/v1/fp" ‖ cbor([[name, table_hash], …]))

The seven ops: create_table, add_column, drop_column, drop_table, insert, update, delete. They hold literal typed values and name rows by primary key, and they carry no row slot. In a table file and in the fingerprint, each row is [cells…, row_slot].

The local copy on disk

Derived state that can always be rebuilt from the chain, so all of it may be deleted. A table file holds exactly the bytes its table_hash covers, so its name is proof of its content.

mycopy/
├── heads/
│   └── 000000000042     the head file, named by slot,
│                        written after every table file it names
├── tables/
│   ├── 3f9a…c21e        table file = sha256 of its own bytes
│   ├── 7b02…e8d4        a table a checkpoint left unchanged
│   └── a5c7…10f9        keeps its file
└── pin                  present iff the copy is pinned

<depot>/chaintables/records/<ns>/<bucket>/<key>
                         record cache, machine-wide
                         (or $CHAINTABLES_CACHE_DIR, or Chain(…; cache_dir))

Verifying a table means hashing a file. The fingerprint check then compares the head's table list against the record's state_fingerprint.

When things go wrong

Each failure has its own name because each one has a different culprit and a different next move. Recovery is always explicit, and nothing heals silently (ADR-0014, ADR-0020).
